## Цель

Привести продукт в соответствие с ответами организаторов на вебинаре (74 вопроса). Полное соответствие
вопрос → решение — в [docs/webinar-qa.md](../docs/webinar-qa.md).

## Область изменений

1. Данные: заглушка выручки (≤ 1000 ₽), артефакты обезличивания, переводы себе, контрагенты вне выборки,
   крупный бизнес по выручке группы, статус клиента, значимость через компанию группы, формулировки платежей.
2. Доступ: только действующие клиенты; несколько компаний у пользователя с переключателем.
3. Инсайт: тип «Гипотеза», шкала влияния с определениями и чувствительностью, дисклеймер, чистота раздела банка.
4. Действия: обращение к менеджеру, обратный звонок, заявка на продукт; скрыть и вернуть событие.
5. Уточнение профиля пользователем: «Важно», «Не учитывать», добавить фактор.
6. Новости: обновление внутри приложения по расписанию, статус источников, кнопка обновления.
7. Документация: версии компонентов, решения D-012…D-015, README, docs/webinar-qa.md.

Вне области: интеграция с CRM банка, push-уведомления, внешняя отраслевая статистика, эмбеддинги.

## Требования и критерии приёмки

- Профиль: `U_ANON` исключён, `U_STUB_REV` без выручки, переводы себе не попадают в контрагентов,
  `U_G42_RENT` (2,1 млрд) — крупный по выручке группы.
- Пользователь компании-prospect получает 403 `not_client`; `cfo_a` переключается между 3 компаниями,
  к чужой компании — 403; запись пользователя в БД не меняется.
- Последствия в инсайте имеют тип `hypothesis`; раздел банка содержит только `bank`; есть `impact`
  с уровнем, оценкой и основаниями; ответ API содержит `disclaimer` и `impact_scale`.
- Скрытое событие пропадает из ленты и появляется в фильтре «Скрытые»; обращение к чужому инсайту — 404.
- Отметки факторов меняют веса, видны как «указано пользователем» и сохраняются при перезагрузке данных.
- Офлайн-метрики ранжирования не ухудшились.

## Проверки

pytest, ruff, `tsc`, сборка UI, `make eval`, сценарии в headless Chromium (лента, карточка, действия,
переключение компании, профиль, качество, демо-хост, чат).

## Риски

- Новые таблицы создаются `create_all`; для применения изменений синтетических данных нужен `seed --reset`.
- Сбор новостей в процессе приложения при нескольких инстансах нужно включать только в одном.
- Пороги шкалы влияния подобраны на синтетике.
